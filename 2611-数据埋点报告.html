三个和通用模型不一样的地方Three differences from the generic model

  1. Data Explorer 的成功是导出，不是渲染。用户不在 Meridian 里做分析，导出到 Excel 再做，报表渲染只是中途。「加载了但没导出就离开」单独计一类，先观察，不判成败。Success in Data Explorer is the export, not the render. Users do not analyse inside Meridian; they export to Excel and work there, so rendering is only a midpoint. "Loaded but left without exporting" is its own group: we watch it first, and do not call it success or failure yet.
  2. Forecast Calculation 的容器是 run_id，不是 idVisit。计算要跑很久（可能一小时以上），用户提交完就走——等 finished 回来时，他那次访问早就被 Matomo 判定结束了。所以这条 journey 装不进一次访问里：提交动作在某次访问里找得到，但 journey 从提交那一刻起就跟着 run_id 走。The container for Forecast Calculation is run_id, not idVisit. A calculation can run for an hour or more and users leave after submitting. By the time finished comes back, their visit has already closed in Matomo. So this journey does not fit inside one visit: the submit action sits in a visit, but from that moment the journey follows run_id.
  3. 受理 ≠ 完成。按 accepted 算成功率会虚高——那只说明请求被收下了。Accepted is not finished. Using accepted as success inflates the number. It only means the request was taken.

前端校验错误怎么补How to add front-end validation errors

日志里只有发出去的请求，所以「点了 Run 但被前端拦下来」这类失败完全看不见。而且它现在会被算成沉默失败——有意图信号、没有 error、也没到成功信号。所以沉默失败率现在是虚高的。The log only holds requests that were sent, so "clicked Run but the front end blocked it" is invisible. Worse, it is counted as a silent failure today: intent signal present, no error, no success signal. So the silent failure rate is inflated right now.

这是埋点，不是现成的数据。Matomo 只记录页面明确推给它的事件，不会自动捕获表单校验。tracker 已经在了，不用搭新东西，但每个拦截点都要前端加一行代码。This is instrumentation, not data we already have. Matomo only records events the page explicitly pushes; it does not capture form validation by itself. The tracker is already in place, so nothing new has to be built, but the front end has to add one line at each trigger point.

四条约束，不然会炸：Four constraints, or this will blow up:

  • 同一个字段、同一条规则，一个任务内只报一次。用户改了又错、错了又改，不要报五遍。One event per field per rule per task. If the user corrects it and trips the same rule again, do not send it five times.
  • 一次点击只报一条。多个字段同时错就报第一个阻塞原因加错误个数，否则一次点击出八条事件，分布就乱了。One event per click. If several fields fail, report the first blocking reason plus the error count. Otherwise one click produces eight events and the breakdown is meaningless.
  • 只覆盖这两条 journey 的提交点：Forecast 的 Run、Data Explorer 的参数 Apply 和导出。不是全站表单。Only cover the submit points of these two journeys: Run in Forecast, Apply and Export in Data Explorer. Not every form in the product.
  • eventName 用规则 ID，不用用户看到的文案。文案会改，而且可能带业务内容。Use a rule ID for eventName, not the message the user sees. Copy changes, and it may contain business content.

工作量是在 2–4 个拦截点各加一次 tracker 调用，半天。The work is one tracker call at each of 2–4 points. About half a day.

上线后拿它做交叉验证：一个任务进到 setup、停留超过 N 秒、却始终没有产生提交请求——这类占比应该和校验错误事件的量级对得上。对不上说明拦截点漏了。Cross-check it after go-live: tasks that reach setup, stay more than N seconds, and never produce a submit request should be about the same size as the validation event count. If they do not match, a trigger point was missed.

P0 是第一版必须有的七个，P1 有余力就出，P2 进第二阶段。三条写死的口径：分子按 journey 计不按 error 次数计；Efficiency 只算成功的 journey；Calculation 的耗时拆用户耗时与系统耗时两段。The seven P0 metrics are required for the first version. P1 if there is time, P2 moves to phase two. Three definitions we fix now: count journeys, not error occurrences; Efficiency covers successful journeys only; split Calculation time into user time and system time.

Forecast Calculation 的体验问题不在成功率上。计算跑一小时，没人坐在那儿等——成功率基本是系统可靠性，不是体验。这条 journey 真正该管的是三件：提交前有没有被挡住（setup 的报错率）、提交后才发现假设错了要重跑（重跑率）、跑完多久才有人知道（知晓延迟）。The experience problem in Forecast Calculation is not the success rate. A run takes an hour and nobody sits and waits, so success rate mostly measures system reliability. What matters here is three things: were they blocked before submitting (setup error rate), did they only find the wrong assumption after submitting (rerun rate), and how long before anyone knew it was done (time to awareness).

停留时长要小心用。timeSpent 是「这个动作到下一个动作」之间的时间，是推算的不是测的。一次访问的最后一个动作没有下一个动作，timeSpent 通常记成 0——用户打开报表认真看了十分钟然后关掉，恰好被记成 0。而且停留长分不出「在认真看」和「找不到想要的列」。它可以做 Efficiency 的基线（那里算的是到成功信号的耗时，有明确终点），但不能用来证明报表被好好使用了。Be careful with dwell time. timeSpent is the gap between one action and the next, so it is derived, not measured. The last action in a visit has no next action, so it is usually recorded as 0 — a user who reads a report carefully for ten minutes and then closes the tab is recorded as 0. A long dwell also cannot tell "reading carefully" from "cannot find the right column". It works as a baseline for Efficiency, which has a real end point, but it cannot prove the report is being used well.

画图的四条规矩Four rules for charts

  • 能用表就不用图。给 Sponsor、Platform Lead 那一层看的是三个数字和一张清单。Use a table unless a chart adds something. What the Sponsor and the Platform Lead need is three numbers and one list.
  • 图只回答两件事：分布和关系。分布用条形 / 直方图，关系用散点。不用饼图、不用双轴、不用三维。Charts answer only two questions: distribution and relationship. Bars or histograms for distribution, scatter for relationship. No pie charts, no dual axes, no 3D.
  • 每张图标出样本量 n。n < 30 标注「样本小」，n < 5 不出数。Show the sample size on every chart. Mark "small sample" below 30, show nothing below 5.
  • 颜色只用来分「要管的」和「不用管的」。不超过两种。Colour only separates "needs action" from "does not". Two colours at most.

模板怎么做到既好看又能复用Making the template look good and still be reusable

固定四块不变，每块的视觉形式也固定——月月只换数字，不重新设计。这是可复用的前提。在这个基础上，三个地方值得做得好看一点：The four blocks stay fixed, and so does the visual form of each block: only the numbers change each month, nothing gets redesigned. That is what makes it reusable. On top of that, three places are worth making striking:

一、四象限散点（主视觉）。x 轴受影响次数，y 轴受影响人数，一个点一个问题，四个象限标上名字：右上「普遍问题，改设计」、右下「少数人反复撞，去找这几个人」、左上「影响面广但偶发，观察」、左下「暂不处理」。这是整份报告唯一需要看图的地方，也是最容易被记住的一张。2×2 这种东西领导天然买账，而且这里它是诚实的——不是为了好看硬凑的框架。1. A four-quadrant scatter as the hero chart. x is tasks affected, y is users affected, one dot per problem, and each quadrant is labelled: top right "widespread, fix the design", bottom right "a few people hitting it repeatedly, go talk to them", top left "broad but rare, watch it", bottom left "not now". This is the one chart in the report that needs looking at, and the one people remember. A 2×2 lands well with senior readers, and here it is honest rather than a frame forced on the data.

二、journey 漏斗。起点 → 意图信号 → 关键步骤 → 成功信号，四段逐级收窄，每段标人数和流失。它直接长成我们 journey 模型的样子，换一条 journey 只换数据不换结构——这就是可复用。2. A journey funnel. Start, intent signal, key steps, success signal — four narrowing bars with the count and the drop-off at each. It is shaped like the journey model itself, so a different journey changes the data, not the structure. That is what reusable means here.

三、问题清单里的迷你趋势。每条问题后面一个 sparkline，三个月的走向。占地小，信息密度高。第二期才有内容，第一期留空位。3. A sparkline per problem. A tiny three-month trend at the end of each row in the problem list. Small, dense, and reserved: empty in phase one, filled from phase two.

不要做的：仪表盘、雷达图、饼图、双轴、3D、发光数字。这些第二个月就会显得很蠢，而且没法复用。What not to build: gauges, radar charts, pie charts, dual axes, 3D, glowing numbers. They look dated by month two and they do not carry over.

任务切分规则（草案，本周要验证的就是它）Task splitting rule (draft — this is what we test this week)

这套规则只用于 Data Explorer。Forecast Calculation 的容器是 run_id，不走 idVisit——计算跑一小时，提交人的访问早就结束了。This rule applies to Data Explorer only. Forecast Calculation uses run_id as its container, not idVisit: a run takes an hour and the submitter's visit has long closed.

在同一个 idVisit 内，按 actionDetailsIndex 排序，遇到下面任一情况就切一刀：Within one idVisit, sorted by actionDetailsIndex, cut whenever any of these happens:

1. eventCategory changed  (Data Explorer / Forecast Calculation / Home)
2. gap between two timestamps > 10 min
3. a successful export — the next action starts a new task

两刀之间的一段 = 一个 journey。要验证的是这三条够不够、会不会切太碎。Everything between two cuts is one journey. What we test is whether three rules are enough, and whether they cut too finely.

「人工看 20 条」具体怎么做What "read 20 by hand" actually means

  1. 挑 20 条，不要随机。故意挑难的：几条很短的（2–3 个动作）、几条很长的（20+）、几条带 401/403 的、几条同时出现 Data Explorer 和 Forecast Calculation 的、来自不同的人。规则要能扛住乱的，不是扛住干净的。Pick 20 on purpose, not at random. Deliberately pick hard ones: a few very short (2–3 actions), a few long (20+), some with 401/403, some that contain both Data Explorer and Forecast Calculation, from different people. The rule has to survive messy visits, not clean ones.
  2. 摊成六列看。每条 idVisit 内按 actionDetailsIndex 排序，只留：序号、时间、eventCategory、url（截短）、statusCode、timeSpent。Excel 里筛选加排序就行。Lay it out in six columns. Sort each idVisit by actionDetailsIndex and keep only: index, time, eventCategory, url (shortened), statusCode, timeSpent. Filtering and sorting in Excel is enough.
  3. 当故事读，手工画刀。一行行看下去，在你觉得「这件事做完了，下一件开始了」的地方标一刀，再用一句话写这个人当时想干什么。先不要看规则，凭判断。Read it as a story and mark the cuts by hand. Go row by row, mark where one task ends and the next begins, and write one line on what the person was trying to do. Do this before looking at the rule.
  4. 再让规则跑一遍，对位置。三条规则机械地切一次，看刀落的地方和你画的一不一样。Then run the rule and compare. Apply the three rules mechanically and see whether the cuts land in the same places.
  5. 只看对不上的。每一处分歧不是规则错，就是你漏了上下文。两种都有用。Only look at the disagreements. Each one means either the rule is wrong or you missed context. Both are useful.

过关线：20 条里有 18 条的刀落在同一个地方。差太多就调规则（通常是那个 10 分钟的阈值，或者要加一条新的切刀），调完换一批新的 20 条再验一次——别在同一批上反复调，那是在拟合样本。Pass mark: the cuts match on 18 of 20. If it is far off, adjust the rule — usually the 10-minute threshold, or a new cut condition — then test on a fresh set of 20. Do not keep tuning on the same sample; that is fitting to it.

判断由 UX 做，数据分析负责备数和跑规则。UX makes the judgement calls; the analyst prepares the data and runs the rule.

验不过怎么办（降级方案）：如果调了两轮还是对不上，第一版退回到访问级——一次 idVisit 算一个任务，成功率就是「这次访问里有没有导出成功」。口径粗，但分母清楚、能解释，而且不耽误 11/20。任务级切分推到第二期，等拿到更多数据再定。不要为了保住任务级切分而推迟出数。If it cannot be validated (fallback): after two rounds of adjustment, fall back to visit level for the first version — one idVisit is one task, and success is simply whether that visit contained a successful export. It is coarser, but the denominator is clear, it can be explained, and 11/20 still holds. Task-level splitting moves to phase two once there is more data. Do not delay the first numbers to save the task-level rule.
